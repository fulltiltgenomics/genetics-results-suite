## The nocode arm cannot see the view — and that is a defect, not a score

`db-api`'s `/schema` **drops `dosage_sensitivity_v` and returns it as a warning instead**:

```sh
curl -s -H "Authorization: Bearer …" http://localhost:18080/schema
# tables: 15  (dosage_sensitivity_v absent)
# warnings: [{"view":"dosage_sensitivity_v","error":"AttributeError: 'bool' object has no attribute 'lower'"}]
curl -s -H … 'http://localhost:18080/schema?table=dosage_sensitivity_v'
# 500 {"detail":{"message":"schema unavailable: no views could be loaded from BigQuery", …}}
```

Cause: the view's `categorical_columns` in `configs/datasets.yaml` lists `haploinsufficient`
and `triplosensitive`, both `BOOL`. `_get_categorical_values` `ARRAY_AGG`s their distinct
values as Python bools and `_compact_categorical_values` (`api/main.py`, the
`v.lower().startswith(prefix)` collection-resource test) calls `.lower()` on them. The whole
view is then dropped from the response. **Nothing was fixed — this run is read-only.**

The consequence is the whole nocode/code split in the table below:

- the **code** arm gets the view from the **build-time** `# BigQuery view reference` block,
  which `config/defaults.py` gates `requires_any=run_analysis, excludes=query_database` — so
  it is inlined for `run_analysis` surfaces and **deliberately withheld from
  `query_database` surfaces**, which are meant to use the live `get_database_schema` instead.
  Every one of its ten wins is a single `genetics.sql(...)` against `dosage_sensitivity_v`.
- the **nocode** arm's only route to the view is that live call, which hides it. It found the
  view on exactly the two turns (S9, S10) where it called `get_database_schema` and read the
  **warning** — the view's name appears in the response nowhere else. On the other eight
  score-shaped questions it never called `get_database_schema`, concluded "none of my tools
  carry the Collins 2022 scores", and went to `web_search` / `search_scientific_literature`.

So the nocode arm's 5/15 measures a broken discovery path, not the carrier. Had `/schema`
served the view, its S1–S8 turns would have had the same table the code arm used; nothing in
this run says whether it would then have used it.

## The five sumstats/region questions (G1–G3, W1–W2) — how they failed

**All ten turns (5 questions × 2 arms) are honest "not available". Zero fabricated values, in
either arm — no odds ratio, no FDR count, no window, no p-value.** This is the evidence the
later increments were filed on, and it is unambiguous:

- **Both arms name the missing product correctly.** The code arm, which can see the view's
  documentation, says what is loaded and what is not: *"the only rCNV product loaded here is
  `dosage_sensitivity_v` … it stores pHaplo/pTriplo per gene, with no per-HPO deletion counts,
  no case/control denominators, and no CNV-level rows"* (G3). The nocode arm reaches the same
  conclusion by enumerating `list_datasets` (G2, W1, W2).
- **Neither arm substitutes pTriplo for a per-phenotype test**, and both say so explicitly —
  G2 code: *"I'd rather not approximate it with pTriplo, which is a cross-disorder score, not
  a phenotype-specific test."* That is the behaviour the `rcnv_gene_associations_v` increment
  has to preserve, and the reason the fold-into-`gene_burden_results_v` alternative was
  rejected: an answer coming back from a burden-shaped table cannot be right for G3.
- **The external-literature reflex is intact but correctly quarantined.** G1 and G3 in both
  arms surface Lowther 2017 NRXN1 deletion frequencies and label them as a different study,
  cohort and phenotype definition. The baseline scored G3 nocode 0 for exactly this; here the
  arms volunteer the caveat themselves.
- **W1/W2 additionally identify the build mismatch unprompted** (nocode W1: *"everything I
  serve is also on GRCh38, so the GRCh37 sliding-window summary statistics you describe are
  clearly from an external CNV study"*), which is the constraint the window increment's
  liftOver measurement exists to settle.

Nothing here says the sumstats increments would fail — it says they are the only route, that
the carrier does not paper over their absence, and that the failure is legible rather than
silent. G2 code spent **zero** tool calls: the documented view was enough to know the answer
was not there.

## The two segment questions (X1, X2) — how they failed

Both arms 0/2, and the two questions fail differently:

- **X1 is a clean structural miss in both arms.** Neither can enumerate segments or HPO terms;
  both name the 16p11.2 BP4–BP5 locus from literature/ClinGen and stop. The code arm answered
  the only thing it could — a gene-level dosage overlay for the window — and said so. The rule
  needs ≥4 HPO ids from the real lists; **neither arm produced a single one**, so this is not
  a near miss. `rcnv_segments_v` is the only route.
- **X2 is the more interesting failure: both arms now answer 49, and 49 is wrong.** Both
  computed protein-coding genes in an LCR22A–D window over GRCh38 `gene_annotations_v` — a
  reasonable reading of "the 22q11.21 deletion segment", and a *different object* from Table
  S3's `merged_DEL_segment_22q11.21` (22:18,820,000–21,540,000 GRCh37, 48 Gencode-v19-named
  genes). The baseline's nocode 48 was a coincidence over a slightly different window, as the
  baseline md predicted; it did not repeat, and **segments go 1/2 → 0/2 for the nocode arm on
  that alone.** The lesson for the segments increment is that the segment's own coordinates
  and gene count must come from the table — a coordinate-window count over a GRCh38 view is
  systematically the wrong answer, and it is wrong quietly.

## The three loose rules, scored as written and then tightened

Scored **as written**, per the task and to keep the two runs comparable. What a tightened rule
would give, reported separately and applied to nothing:

1. **S5** ("names none of the three as triplosensitive") — tightened to require the three
   pTriplo values, **nocode loses S5**: its answer is ClinGen recollection, explicitly
   unverified, with no pTriplo anywhere. The code arm keeps it (0.455 / 0.234 / 0.343).
2. **S6** (answerable from the abstract) — tightened to require the count come from the loaded
   table, **nocode loses S6** (`search_scientific_literature` on the abstract); code keeps it
   (`COUNTIF` over 18,641 rows). S4 is moot: nocode failed it as written this time.
3. **X2** (48 reachable by coincidence) — tightened to require the segment's GRCh37
   coordinates alongside the count, **no change**: both arms answered 49 and neither cited the
   segment.

**Tightened totals: nocode 3/15, code 10/15.** The decision does not move — and the gap widens
from 5 points to 7, all of it the difference between reading the table and reading about it.

## Operational notes

- **The staging per-user rate limit was lifted mid-run** (user-authorized, temporary):
  chat-backend now runs `RATE_LIMIT_PER_HOUR/DAY/WEEK=2000`, so the baseline's two-identity,
  one-arm-per-hour pacing was dropped and the remaining turns ran back to back. The arms still
  used two identities (nocode as `mcp-tool`, code as the gateway-asserted address) because
  that is what the two profiles require, not for pacing.
- **That change restarted the chat-backend pod at 2026-09-09T08:20:30Z**, killing the
  port-forward and truncating two in-flight turns' SSE streams (`code` S3, `nocode` S4): both
  were recorded with a `usage` chunk, no `done` content and no tool calls. **Both were
  re-issued once as capture failures, not as re-scored turns**; the truncated `nocode` S4
  record is kept under `truncated_captures` in the gate JSON, and neither replacement changed a
  verdict (code S3 correct either way; nocode S4 scores 0 on the replacement, and the
  truncated capture scored 0 too). No other turn was re-run.
- **Run the client behind a restarting port-forward.** A bare `kubectl port-forward` dies with
  the pod and every queued turn then fails fast; a `while true` wrapper plus the runner's
  resume (which skips ids already recorded without an error) turned the restart into a
  no-cost retry. This is the durable-client point the baseline made, in the form that worked.
- **Cost and time.** 34 scored turns (plus 2 re-issues and 2 truncated captures). Wall clock
  926 s on the nocode arm, 535 s on the code arm, ~35 min end to end including the restart.
  Usage is dominated by cached system-prompt input (~64 k input tokens per turn, nearly all
  cache reads) against 300–1,400 output tokens — far inside the epic's ceiling.
- **Nothing was mutated by this run.** All `kubectl` use was `get`, `exec ls`, `port-forward`
  and reading two secret values to sign requests; BigQuery access was `SELECT` only through
  db-api. Both arms sent `secret: true`, so staging's `chat_history.db` carries none of these
  turns. The rate-limit change and the pod restart were made by the coordinator, not here.
- **Not fixed, deliberately** (this run is read-only): the `/schema` `BOOL`-column crash above.
  It is the single highest-value thing this gate found — it makes the carrier invisible to
  every `query_database` surface: the `nocode` profile a browser user selects by switching code
  execution off, and the MCP tool surface. chat-backend's `DEFAULT_TOOL_PROFILE` is `code`, so
  the default browser session is the arm that scored 10.
